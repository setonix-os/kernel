## 2. CI workflows

The reference has six workflows: `ci_main.yml`, `ci_pr.yml`, `links.yml`, `cleanup_caches.yml`,
`release.yml` and `registry-publish.yml`. The target has two: `ci_main.yml` and `ci_pr.yml`. Every
target job runs inside the devcontainer through `devcontainers/ci`, and
`.github/scripts/check-toolchain-pin.sh:73-108` forbids `dtolnay/rust-toolchain`,
`actions-rs/toolchain`, `actions/setup-{node,python,go,java}`, `sh.rustup.rs`, `rustup default` and
`rustup toolchain install` anywhere under `.github/workflows/`. So **any tool the reference installs
inside a workflow step must instead go into `.devcontainer/Dockerfile`, pinned and verified.** That
rule shapes every ADAPT below.

### 2.1 Least-privilege permissions

- **Reference:** read-only at workflow level, with a comment stating the policy
  (`ci_main.yml:3-7`). Elevated scope is granted per job: `ci-success` gets `actions: write` for cache
  cleanup (`ci_main.yml:335-338`), and in `release.yml:6-7` only the `release` job gets
  `contents: write`, `id-token: write` and `attestations: write` (`release.yml:521-524`). Every other
  job restates `contents: read` (`release.yml:41-42, 209-210, 416-417`).
- **Target:** `ci_pr.yml:3-8` is read-only plus `packages: read`, which is good. But `ci_main.yml:3-8`
  grants `packages: write` at **workflow** level, so the `checks` job holds write scope to GHCR even
  though it runs `push: never` (`ci_main.yml:43`). Only `boot` pushes (`ci_main.yml:125`).
- **Recommendation: ADAPT.** In `ci_main.yml`, set the workflow level to `contents: read` and
  `packages: read`, and give the `boot` job its own `permissions: { contents: read, packages: write }`
  with the existing "write on main" comment moved beside it. Small; changes `ci_main.yml`. No decision
  needed.

### 2.2 `workflow_dispatch`

- **Reference:** `ci_main.yml:13` and `ci_pr.yml:13` let the maintainer re-run CI by hand.
- **Target:** neither CI workflow has it (`ci_main.yml:10-12`, `ci_pr.yml:157-159`).
- **Recommendation: ADAPT.** Add it to `ci_main.yml`, but **guard the publish**. `ci_main.yml:125`
  pushes with `push: always`, so a dispatch on a feature branch would publish that branch's image as
  the cache every pull request trusts, which is exactly what `ci_pr.yml:3-7` exists to prevent.
  Either use `push: ${{ github.ref == 'refs/heads/main' && 'always' || 'never' }}` or add a job-level
  `if:`. The main use is republishing the image after a GHCR incident. Small; changes `ci_main.yml`.

### 2.3 PR trigger breadth and `merge_group`

- **Reference:** `ci_pr.yml:7-11` uses `pull_request: branches: ["**"]` plus `merge_group`.
- **Target:** `ci_pr.yml:158-159` uses `branches: [main]` only. A **stacked** pull request (one whose
  base is another feature branch) gets **no CI at all**. Stacked PRs are the natural way to deliver
  the "small, separately reviewable increments" that §5.3 asks for.
- **Recommendation: ADAPT** `branches: ["**"]`. The concurrency group keyed on
  `github.event.pull_request.number` (`ci_pr.yml:161-163`) stays correct for `pull_request`.
  **SKIP `merge_group`** unless the maintainer turns on a merge queue. The `main` ruleset's
  `allowed_merge_methods: ["merge"]` and the sole-merger rule (§5.1) suggest he will not, so that is a
  **DECIDE**. If either 2.2 or `merge_group` is added to `ci_pr.yml`, change the concurrency group to
  `${{ github.workflow }}-${{ github.ref }}` as the reference does (`ci_pr.yml:15-19`): the PR number
  is empty for those events.

### 2.4 `RUSTFLAGS` is not reaching cargo (target defect)

- **Reference:** `RUSTFLAGS: "-Dwarnings"` in workflow `env` (`ci_main.yml:19-21`). It works there
  because the steps run on the runner.
- **Target:** copied the same block (`ci_main.yml:18-21`, `ci_pr.yml:165-168`). Inside
  `devcontainers/ci` it is **dead**: the CI log shows only `GITHUB_*` variables passed through
  `--remote-env`. Clippy is unaffected, because every clippy call passes `-- -D warnings` explicitly.
  But every `cargo build` and `cargo test` in `runCmd` (`ci_pr.yml:229-230, 235, 241, 249`), and
  `cargo xtask boot-test`, accept rustc warnings silently. `CARGO_TERM_COLOR` is equally dead.
- **Recommendation: ADAPT (bug fix).** Pass the variables through the action's `env:` input, which
  `devcontainers/ci` turns into `--remote-env`, keeping the workflow `env` as the single source:
  `env: | RUSTFLAGS=${{ env.RUSTFLAGS }}` and `CARGO_TERM_COLOR=…`. Do this in all four
  `devcontainers/ci` steps, or set them at the top of each `runCmd`. **Expect it to surface warnings
  that are currently ignored.** Small; changes `ci_main.yml` and `ci_pr.yml`. Land it first, on its
  own.

### 2.5 `--locked`

- **Reference:** every build, test, clippy and check runs with `--locked` (`ci_main.yml:163-181`,
  `ci_main.yml:249`, `release.yml:249-260`). The reason is written down in `RELEASING.md:219-225`: a
  `Cargo.toml` change with a stale lockfile fails on its PR, not later.
- **Target:** `Cargo.lock` is committed on reproducibility grounds (`CLAUDE.md` § Toolchain;
  `.gitignore:5-6`), yet no CI invocation uses `--locked` (`ci_pr.yml:228-249`). Nor does `xtask`'s
  own build (`xtask/src/main.rs:232-245`). Today the lockfile holds only workspace members, so the
  exposure is a member's version or name changing without a lockfile update. The rule should be in
  place before the first external dependency arrives (vendored Redox crates, per `CLAUDE.md`).
- **Recommendation: ADOPT.** Add `--locked` to every cargo command in both workflows. Give
  `cargo xtask` a way to pass it through (or have `build()` always pass it), so the boot tests are
  locked too. Small; changes `ci_main.yml`, `ci_pr.yml`, `xtask/src/main.rs` and the
  `CONTRIBUTING.md` § Development Setup command block. No decision needed.

### 2.6 Rustdoc check

- **Reference:** `cargo doc --no-deps --document-private-items` with `RUSTDOCFLAGS: "-Dwarnings"`
  (`ci_main.yml:98-101`, `ci_pr.yml:93-96`).
- **Target:** `missing_docs = "warn"` (`Cargo.toml:47`) and a rule that every public item carries a
  doc comment (`STYLE.md:105`). But nothing builds the docs, so broken intra-doc links, malformed doc
  tests outside the test run, and `rustdoc::` lints never fail CI. The capability crate leans heavily
  on doc tests, including a `compile_fail` (`CHANGELOG.md:18-21`); those run under `cargo test`, but
  the documentation build itself does not.
- **Recommendation: ADAPT.** Add a "Documentation" group inside the `checks` `runCmd`, scoped by
  package (CLAUDE.md requires it):
  `cargo doc --locked --no-deps --document-private-items --package setonix-kernel --target <each Tier-1>`,
  then the same for `--package setonix-capability` and `--package xtask`, with `RUSTDOCFLAGS=-Dwarnings`
  forwarded as in 2.4. Add the command to `CONTRIBUTING.md` § Development Setup and to the PR
  requirements. Small to medium (it may surface doc warnings). Changes both workflows and
  `CONTRIBUTING.md`.

### 2.7 Internal link and anchor checking (lychee, offline)

- **Reference:** gates every PR and main push on
  `lychee --offline --include-fragments … "./**/*.md"` (`ci_pr.yml:77-91`, `ci_main.yml:67-89`).
  lychee comes from a pinned release archive with a SHA-256 check rather than an action, so the
  allow-listed set of actions does not grow (comment at `ci_pr.yml:77-83`). It is also in the PR
  requirements (`CONTRIBUTING.md:102`).
- **Target:** has no link checking. The target's documents are dense with relative links and
  anchors: 38 relative Markdown links and 12 with `#fragment` across the tree, and the constitution,
  RFCs and research notes cite one another constantly. `CONTRIBUTING.md:113-116` warns that
  "citations break silently". `/check-coherence` catches orphaned claims, but only when someone runs
  it.
- **Recommendation: ADAPT.** Under the devcontainer rule, lychee cannot be installed by a workflow
  step. Add a `lychee` stage to `.devcontainer/Dockerfile` in the file's own idiom: an
  `ARG LYCHEE_VERSION`/`ARG LYCHEE_SHA256` pair, a download from the GitHub release, a
  `sha256sum --check`, then `COPY` into the final image and a `lychee --version` line in the
  verification block (`Dockerfile:306-329`). Then:
    - add a "Links" group to both workflows' `checks` `runCmd`;
    - add a PR-requirements line in `CONTRIBUTING.md` and the PR template;
    - add the command to `/check-style`;
    - add `"**/node_modules/**"` to `.markdownlint-cli2.jsonc` while there (the reference ignores it;
      the target ignores it only in `.gitignore`).

  § `x.y` prose citations are not links and stay `/check-coherence`'s job; say so in the PR. Medium
  (Dockerfile stage plus fixing whatever it finds). Changes `.devcontainer/Dockerfile`, both
  workflows, `CONTRIBUTING.md`, `.github/PULL_REQUEST_TEMPLATE.md` and the check-style command or
  skill. No decision needed: it follows §7's "the image must be able to run every check a contributor
  is asked to run".

### 2.8 Scheduled external-link check

- **Reference:** `links.yml:1-56`. Weekly cron off the hour (`"17 6 * * 1"`, `links.yml:12-13`),
  `workflow_dispatch`, read-only permissions, timeout, `--max-retries 3`, `--accept 200..=299,403,429`,
  and per-host exclusions each justified in a comment (`links.yml:43-56`). It is kept off the PR path
  because third-party sites fail on their own schedule (`links.yml:3-6`).
- **Target:** none. The research and RFC documents cite external papers (cs.fsu.edu, usenix.org,
  acm.org, sel4.systems and others: 65 external URLs in Markdown). Under §5.5 that is citation
  integrity, not cosmetics.
- **Recommendation: ADAPT.** Add a new `.github/workflows/links.yml` that runs lychee **inside the
  devcontainer image**: `devcontainers/ci` with `cacheFrom` the GHCR image and `push: never`, so it
  uses the lychee from 2.7 and installs nothing. Keep the reference's cron style, retries, accept list
  and comment-per-exclusion rule. Small, after 2.7. Adds `.github/workflows/links.yml`. Note that it
  needs `packages: read` like `ci_pr.yml:8`.

### 2.9 Build cache: restore/save split, write on main only

- **Reference:** `actions/cache/restore` everywhere, `actions/cache/save` only on main and only on a
  cache miss, with `continue-on-error` for save races (`ci_main.yml:139-161, 194-217`). PR runs are
  restore-only (`ci_pr.yml:131-152`, comment "Restore cache from main branch (read-only)").
- **Target:** the same discipline, applied to the **image**: `cacheFrom` GHCR everywhere, with
  `push: always` only in `ci_main` `boot` after the checks and boots pass (`ci_main.yml:113-125`;
  rationale at `ci_pr.yml:3-7, 175-178`). There is no `target/` cache, which is reasonable: the
  workspace has zero external dependencies (`xtask/Cargo.toml:11-15`, `capability/Cargo.toml:11-14`).
- **Recommendation: KEEP.** The target's "publish only after proving it builds and boots" is
  stricter than the reference. Revisit a `target/` cache only when vendored crates make cold builds
  slow.

### 2.10 Cache cleanup

- **Reference:** a manual `cleanup_caches.yml` (dry-run by default, `cleanup_caches.yml:5-14`;
  non-cancelling concurrency group, `:18-20`; job-level `actions: write`, `:28-30`) that `require`s
  `.github/scripts/cleanup-caches.js:1-189`, plus an automatic copy of the same logic inline in
  `ci_main.yml:360-437`.
- **Target:** uses no Actions cache, so there is nothing to clean. **SKIP.** The analogue is GHCR:
  each main push tags `ghcr.io/setonix-os/kernel-devcontainer:latest` and leaves the previous
  manifest untagged, so untagged versions accumulate. (The org packages API is not reachable from
  this session, so the count was not verified.) **Optional ADAPT:** a manual, dry-run-by-default
  workflow that prunes untagged versions older than N. It needs either a new third-party action or
  `gh api` calls with `packages: write`. **DECIDE:** it adds an action to the allow-list (or bespoke
  API code) for a storage cost that may be irrelevant to a public package.

### 2.11 OS matrix, release-mode tests, performance bounds, readability oracle

- **Reference:** a three-OS matrix with `fail-fast: false` (`ci_main.yml:111-116`), debug and release
  builds, a release-only performance suite (`:177-181`) and a Python oracle (`ci_pr.yml:174-188`).
- **Target:** a single image; both Tier-1 targets in a loop (`ci_pr.yml:226-237`); debug and release
  builds; debug **and release** boots on main (`ci_main.yml:128-130`) but **only debug** boots on PRs
  (`ci_pr.yml:283-284`). That contradicts `ci_main.yml:23-25`, "Identical to ci_pr.yml except that
  this workflow *publishes*". It also leaves a release-only boot regression to be found after merge,
  even though `ci_main.yml:113-115` says debug-only boot tests "let real faults through in other
  kernels".
- **Recommendation:** **SKIP** the OS matrix, perf suite and oracle (product-specific). **ADAPT** one
  parity fix: add `cargo xtask boot-test --arch aarch64 --release --expect "Kaya!"` to
  `ci_pr.yml:281-284`, or correct the comment at `ci_main.yml:23-25`. The first is preferable. Small;
  changes `ci_pr.yml`.

### 2.12 MSRV job

- **Reference:** `msrv` job reads `rust-version` and runs `rustup toolchain install` then
  `cargo +X check` (`ci_main.yml:219-249`).
- **Recommendation: SKIP.** The target has no `rust-version` and no consumers. It pins one exact
  toolchain (`rust-toolchain.toml:11`). And `rustup toolchain install` inside a workflow is
  **explicitly forbidden** by `check-toolchain-pin.sh:101-108`. Adopting it would conflict with §7.

### 2.13 Coverage

- **Reference:** a `coverage` job with `cargo-llvm-cov` (installed by `taiki-e/install-action`),
  lcov plus summary, a documented exclusion of `main.rs` (`ci_main.yml:251-326`), and a Codecov upload
  with a mandatory token, skipped for Dependabot (`:315-326`, `ci_pr.yml:274-283`). Configured by
  `codecov.yml:1-50` (project threshold 1 %, patch target 80 %) and documented as a 99 % line-coverage
  claim with honest caveats (`CONTRIBUTING.md:257-266`).
- **Target:** none. But the security-critical logic was split into `setonix-capability` precisely to
  be host-tested (`CLAUDE.md` § Layout; `capability/Cargo.toml:11-14`), and `llvm-tools` is already
  in the toolchain (`rust-toolchain.toml:13`). The CHANGELOG reports mutation testing done by hand
  (`CHANGELOG.md:42-43`); nothing keeps it honest afterwards.
- **Recommendation: ADAPT, without upload first.**
    1. Add `cargo-llvm-cov` to the Dockerfile, pinned and verified. It cannot come from
       `taiki-e/install-action`.
    2. Add a "Coverage (capability, host)" group running
       `cargo llvm-cov --locked --package setonix-capability --summary-only`, printed to the log and
       the step summary (2.17).
    3. Optionally, a `--fail-under-lines` gate once the baseline is known.
    4. Add `lcov.info` to `.gitignore`.

  **DECIDE:** Codecov (third-party service, `CODECOV_TOKEN` secret, `codecov/codecov-action` added to
  the allow-list, a badge, `codecov.yml`) is a trust and supply-chain decision. The target's SECURITY
  posture (`SECURITY.md:321-323`) suggests keeping it in-image. Medium. Changes
  `.devcontainer/Dockerfile`, both workflows, `.gitignore` and `CONTRIBUTING.md` § Testing.

### 2.14 `ci-success` aggregator

- **Reference:** `if: always()` and a status check over every `needs` result (`ci_pr.yml:285-305`).
- **Target:** the same shape with `if: ${{ !cancelled() }}` (`ci_pr.yml:286-301`). It is the
  `main` ruleset's single required status check ("CI Success").
- **Recommendation: KEEP.** When new jobs are added (`links` is scheduled, not here), add them to
  `needs` **and** to the shell condition. Forgetting the second part silently weakens the required
  check.

### 2.15 Timeouts

- **Reference:** a `timeout-minutes` on every job, with the reason for an unusual one written down
  (`ci_main.yml:106-109`).
- **Target:** a timeout on every job (`ci_pr.yml:183, 256, 290`). **KEEP.** Add a one-line rationale
  for the 45-minute `checks` timeout: it is presumably the cold image build, QEMU from source.

### 2.16 Concurrency

- **Reference:** `${{ github.workflow }}-${{ github.ref }}`, cancel-in-progress for CI
  (`ci_pr.yml:15-19`). `cancel-in-progress: false` for release, registry and cache cleanup, each with
  its reason (`release.yml:22-28`, `registry-publish.yml:29-31`, `cleanup_caches.yml:16-20`).
- **Target:** equivalent for CI (`ci_main.yml:14-16`, `ci_pr.yml:161-163`). **KEEP**, with the 2.3
  caveat. **ADAPT** one point: on `ci_main`, `cancel-in-progress: true` can cancel a run in the
  middle of `push: always`. Consider giving the publishing `boot` job its own job-level `concurrency`
  with `cancel-in-progress: false`, which is the reference's reasoning that "half-uploaded is worse
  than a queued duplicate" (`release.yml:24-25`). Small.

### 2.17 Step summaries

- **Reference:** writes a human-readable outcome to `$GITHUB_STEP_SUMMARY` (`release.yml:739-747`).
- **Target:** `GITHUB_STEP_SUMMARY` **is** forwarded into the container (CI log, `--remote-env
  GITHUB_STEP_SUMMARY=/mnt/github/step-summary`) but is unused.
- **Recommendation: ADAPT (optional).** Have `cargo xtask boot-test` (or the `runCmd`) append the
  captured serial console and the matched string to the step summary, so a reviewer sees the greeting
  and the decoded `BRK` report without opening the log. Coverage (2.13) can go there too. Small.

### 2.18 Release automation

- **Reference:** `release.yml:1-747` has four jobs. `validate` checks the tag format, the
  `Cargo.toml` version, that the tag is on main, that a CHANGELOG entry exists and that the release
  does not already exist (`:35-200`). `build` packages, unpacks and runs the packaged binary
  (`:202-406`). `bundle` (`:408-507`) builds the MCPB extension. `release` (`:509-747`) checks every
  artefact is present, generates and re-verifies `SHA256SUMS`, attests SLSA provenance, extracts notes
  from the CHANGELOG with verification instructions appended, creates a **draft** with retries, and
  never publishes. A dry run via `workflow_dispatch` (`:15-20`) completes the set.
  `docs/RELEASING.md:1-238` is the runbook: dry run first, stamp the changelog, signed tags, review
  and publish scripts, rollback, "after publishing never move the tag". `scripts/release/
  review-draft.sh` and `publish-draft.sh` are guarded, digest-pinned publish steps.
- **Target:** no releases, no artefacts, no users. `SECURITY.md:273-274` says "pre-release … no
  supported versions". Publication is Phase 4 (`CONSTITUTION.md:295-296`), with season codenames
  (`CONSTITUTION.md:259-266`, `CHANGELOG.md:8`). The `tags` ruleset (signed, admin-only create,
  update and delete) **already exists**.
- **Recommendation: SKIP now; defer to Phase 4. DECIDE when.** The principles transfer directly to
  pillar 3 (author-signed distribution) and should be recorded so they are not reinvented:
    - every irreversible step last and after a human look;
    - draft, then a reviewed publish;
    - the tag on main;
    - a CHANGELOG gate;
    - checksums that are re-verified;
    - provenance attestation;
    - retries with a reusable draft.

  Record them as a TODO entry (5.6) or as the seed of a future release RFC, not as a workflow. Large
  when it is done.

### 2.19 Registry publish, release assets, MCPB, glama, Dockerfile, `.dockerignore`, `build.rs`, `.env.local.example`

- **Reference:** `registry-publish.yml:1-113` (MCP Registry via OIDC);
  `.github/release-assets/{README.md, mcpb-manifest.json, server.json, icon.png}`; `glama.json:1-4`;
  the root `Dockerfile:1-50` (runtime image) with `.dockerignore:1-13`; `build.rs:1-30` (Windows
  version resource for SignPath); `.env.local.example:1-5` (Altium path).
- **Recommendation: SKIP**, all of them: specific to an MCP server, Windows or Altium. Two
  sub-patterns are worth noting:
    - `registry-publish.yml:65-79` installs a publishing binary from a pinned archive with a checksum.
      The target already does this, more thoroughly, in its Dockerfile.
